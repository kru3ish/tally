# Decisions

One line each. Newest at the bottom.

- D1: The working directory held an unrelated Python project (coach), so Tally lives in `~/dev/tally` as a fresh repo on `main`, per the global workspace convention.
- D2: Dependencies are `zod` at runtime and `typescript`, `vitest`, `tsx`, `@types/node` for dev. No CLI framework; args are parsed by hand.
- D3: `TALLY_HOME` overrides `~/.tally`; `CLAUDE_CONFIG_DIR` (Claude Code's own variable) overrides `~/.claude`. The demo and tests set both to temp dirs.
- D4: The hook entry (`dist/hooks/hook.js`) imports only node builtins plus `paths` and `redact`, so node startup dominates its runtime. Measured median is ~70 ms on Windows.
- D5: Two extra hooks beyond the brief's seven: `PostToolUseFailure` (failed Bash runs do not fire PostToolUse) and `Notification` with matcher `permission_prompt` (the only signal for permission friction).
- D6: PreToolUse, PostToolUse, PostToolUseFailure, Stop, PreCompact, Notification run `async: true`; SessionStart, UserPromptSubmit, SessionEnd stay sync because they return context or must run before exit.
- D7: Git HEAD at session start is read from `.git/HEAD` and refs files directly rather than shelling out, to stay inside 150 ms.
- D8: One API response spans several transcript lines with the same `message.id`; usage is counted once per id. Cache writes use the 1h price when `ephemeral_1h_input_tokens` is set, else 5m.
- D9: Phases are deterministic: `explore` until the first Edit/Write, `build` until the first test/lint command, `verify` until a ship command, then `ship`. Every assistant message is charged to the phase active when it was produced.
- D10: Waste dollar amounts: failed loop = cost of each repeat beyond the first; repeated read = cost of each read beyond the first; dead weight = (first-turn context − baseline 15k) priced as one 1h cache write plus a cache read per call; compaction churn = cache-write tokens of messages right after a compaction.
- D11: Tally's own LLM calls use `claude -p --setting-sources "" --strict-mcp-config --tools "" --max-turns 1 --no-session-persistence` from an empty temp dir. Measured: $0.016 per small call instead of $0.35 without isolation. `--bare` is not used because it rejects subscription logins.
- D12: The npm package root is also the plugin root (`.claude-plugin/plugin.json`, `hooks/hooks.json`, `commands/`), and `.claude-plugin/marketplace.json` points at `./`, so one clone serves `npm link`, `--plugin-dir`, and `plugin marketplace add`.
- D13: Uninstall restores the exact original bytes when the parsed settings equal the pre-install snapshot; otherwise it removes only Tally's hook entries and re-serializes with the file's own indentation.
- D14: Ship detection happens in the PostToolUse hook on Bash commands matching `git push`, `gh pr create|merge`, `npm|cargo publish`, `twine upload`, and spawns a detached `tally judge` process.
- D15: The `/insights`, `/fewer-permission-prompts`, `/cost`, `/usage`, `/context` built-ins are referenced by Coach messages, never reimplemented.
- D16: The budget is 25% of the human-equivalent value (hours × hourly_rate) with a $2 floor; one story point = 4 hours; without story points the intake model's hour estimate is used, else 2 hours.
- D17: Verdict is computed, not asked for: `worth it` needs completion ≥70%, ROI ≥2×, quality ≥6 and no failing independent run; `not worth it` when completion <40%, ROI <1× or quality <4; otherwise `borderline`. Completion counts met=1, partial=0.5, unmet and unverifiable=0.
- D18: Value credited = human value × completion %. ROI = credited value / session spend.
- D19: The Judge always uses its own skeptical system prompt; the model is configurable (`models.judge`, default opus) and may coincide with the session model.
- D20: Without a linked task the Judge still runs, with one inferred criterion from the first prompt and spec quality 0, and the report says so.
- D21: Skill/MCP "touched a met criterion" = the call happened in a user turn during which a file cited by a met criterion was edited. Labelled correlational everywhere it appears.
- D22: `tally judge --auto` on session end is skipped when a receipt already exists (a ship already judged it); a ship re-judges and keeps the previous receipt as judge.prev.json.
- D23: Coach noise state is per session (`coach-state.json`); mutes are per repo (`~/.tally/mutes.json`); three skips auto-mute.
- D24: Coach `auto` mode writes only `.md` files; `settings` actions (allowlist entries) only run when the user presses `[a]`; MCP and plugin removal is shown as a command, never executed.
- D25: Dead-weight overhead is the average first-turn context above the 15k baseline across the last N sessions in the repo, shared evenly across loaded items; the message says so and points to `tally experiment`.
- D26: Experiments patch `.claude/settings.local.json` for the next session (`permissions.deny: Skill(name)` for skills, `disabledMcpjsonServers`/`disabledMcpServers` for MCP) and restore the exact prior bytes (or absence) at session end via `tally finalize`. Arms alternate off/on; the assignment is recorded when the first prompt's `tally task --auto` runs.
- D27: Follow-up final verdict: reverted → not worth it; needed rework → one step down; held up → unchanged. Runs on session start when the last run is >24h old, for receipts 7–90 days old.
- D28: Follow-up's revert detection searches `git log --grep=revert` for the PR number, merge sha, or branch name.
- D29: `tally demo` isolates via TALLY_HOME and CLAUDE_CONFIG_DIR, feeds fixture events to the real hook binary, simulates time from event timestamps, and stubs every LLM call.
- D30: Fixture timestamps were stretched to a ~22-minute session so the Coach's 3-minute interval shows its behaviour in the demo.
- D31: Hook path is resolved from the package root (`dist/hooks/hook.js`) so tests running from `src/` and the CLI running from `dist/` agree.
- D32: On Windows the `claude` npm shim is resolved to its JS entry and run with node directly, avoiding cmd.exe quoting of JSON arguments; timeouts kill the whole process tree with taskkill.
- H1-a: Internal `claude -p` calls set `TALLY_INTERNAL=1` and `CLAUDE_CODE_ENTRYPOINT=tally` and run from a `tally-llm-*` temp cwd; hooks exit at once on `TALLY_INTERNAL`. Verified that `--no-session-persistence` leaves no transcript, so tagging is defence in depth (see PLATFORM_NOTES).
- H1-b: `history.jsonl` entries carry `internal`; `loadHistory()` filters them and anything under a `tally-llm-` cwd, so dead-weight, trends and experiment reports never see Tally's own runs.
- H1-c: Every receipt records `cost.tally_own_usd` and `cost.tally_share_pct` (own spend ÷ session spend); `tally doctor` averages the share over receipts and warns above 5%.
- H1-d: Transcript parser records the Claude Code `version`, counts unparseable lines and unknown line types, and marks `cost_confidence: partial` when any are present or the major.minor is not in the verified list (`2.1`). Receipts label the cost PARTIAL and `tally doctor` scans the five most recent transcripts.
- H1-e: `TALLY_CLAUDE_BIN` may point at a `.js` file, which is run under node; tests use it to drive the real launcher with a fake `claude`.
- H2-a: Test re-run consent is stored per repo in `config.consent.test_rerun[repoKey]`. Asked once: by the Coach rule `verification-consent` ([a] grants, [s]/[m] declines) or by `tally judge` at a TTY. `--auto` runs never prompt; without a stored answer tests are simply not run.
- H2-b: Without consent, any criterion whose text mentions tests/spec/coverage/passing/CI is forced to `unverifiable` with evidence prefixed `unverifiable (tests not run: no consent)`, unless the model already marked it unmet. The judge prompt says the same.
- H2-c: Test re-runs get a scrubbed environment: an allowlist of platform variables plus anything that is not credential-shaped (`TOKEN|SECRET|KEY|PASSWORD|AUTH|…`, `TALLY_*`, `CLAUDE_*`, values starting with `sk-`/`ghp_`/`AKIA`/`eyJ`, values over 200 chars). `TALLY_INTERNAL=1` and `TALLY_TEST_RERUN=1` are set so nested hooks stay quiet. The receipt records `verification.command` and `env_scrubbed`.
- H2-d: The judge model's output is passed through `redactDeep` before use, and the write-back comment through `redact`, so a secret echoed from a diff or a message never reaches judge.json, report.md, or an issue comment.
- H2-e: Write-back and follow-up check `gh` first (installed + authenticated) and report "skipped: …" with the install/login fix instead of failing silently.
- H3-a: Per-item context overhead is *measured* only when the repo has sessions both with and without the item loaded (first-turn token delta between the groups); otherwise it is the even share, labelled `estimated` in the title and message.
- H3-b: The dead-weight rule recommends removal only when the overhead is measured or the item has gone unused for 10+ sessions in a row; otherwise it says "watch" with no action.
- H3-c: OTel is an optional cross-check, not a replacement: `tally otel` receives OTLP/HTTP JSON on loopback, receipts show the OTel total and delta when points exist for the session, and a note when telemetry is enabled but nothing arrived.
- H3-d: Revert detection passes git a full ISO `--since` one day before the receipt; a date-only `--since` is parsed at git's local midnight and was observed dropping same-day commits.
- H4-a: CI runs `npm test`, the demo, the calibration eval, and an install/uninstall hash check on ubuntu, macos and windows × Node 18 and 22 (`.github/workflows/ci.yml`).
- H4-b: `tally start` picks per OS: tmux split inside tmux, a new tmux session where tmux exists, a Windows Terminal split when `WT_SESSION` is set and `wt` exists, else it prints the command. Tests clear `TMUX`/`WT_SESSION` and shrink PATH so they never open real panes.
- H4-c: `ghStatus()` (installed + authenticated, cached) gates write-back and follow-up; both report "skipped: <reason>. Fix: <command>" instead of failing silently, and follow-up still runs local revert detection.
- H5-a: Human grades live in `~/.tally/calibration.jsonl` (one entry per session, latest wins); `tally calibrate add <session> --human …` snapshots the judge's statuses and evidence next to the human's so the report can list disagreements with evidence.
- H5-b: Agreement is reported two ways: exact, and "within one step" where partial/unverifiable neighbour the human grade. The confusion matrix has human rows and judge columns.
- H5-c: The five calibration fixtures have answers by construction (each scenario's diff and test outcome are authored to make the grade unambiguous). `expected.json` is the human grade; `model-output.json` is the real judge model's output recorded once with `--live --record`; CI replays it through the pipeline and fails if criterion agreement drops below `baseline.json`.
- H5-d: The replay measures the deterministic pipeline (verification, consent, verdict maths, redaction), not the model; `tally calibrate eval --live` re-measures the model and the README reports the last live numbers.
- H1-f: Measured Tally overhead on the five calibration receipts (opus judge): $0.11–0.13 per receipt, 17–25% of session spend for $0.43–0.73 sessions, 22% average. The 5% target is met only for sessions above about $2.50; the README says so and points at `models.judge sonnet`. Doctor's warning threshold stays at 5%.
- H5-e: Three consecutive live runs gave 19/19, 18/19, 18/19 criteria and 4/5 verdicts; `baseline.json` holds the 18/19 run and CI fails on any drop below it.
- O1: Criteria are classified at intake: `mechanical` when the intake model attaches a check spec (`tests_pass`, `file_exists`, `file_changed`, `file_contains`, `diff_contains`, `command`, `pr`), otherwise `judgment`. Tier 0 resolves mechanical criteria with no model; `command` checks run only the repo's own scripts (package.json scripts, `npx tsc`, `make <target>`, standard test runners) and need the same consent as test re-runs.
- O2: Tier 1 uses `models.tier1` (haiku) on judgment criteria only, with an evidence pack trimmed to `judge.tier1_evidence_tokens` (8k): named-file hunks first, then the rest, then a truncation marker. It returns a confidence per criterion.
- O3: Tier 2 (`models.judge`) runs only when session cost ≥ `judge.deepThreshold` ($3), `--deep` is passed, or a Tier 1 confidence is below `judge.tier1_confidence_floor` (0.6). Cost/--deep triggers send all judgment criteria; the confidence trigger sends only the unsure ones. Tier 2 is skipped entirely (not run after Tier 1) when cost/--deep already select it.
- O4: With no model call, quality, verdict reason and recommendations are a labelled mechanical proxy built from the independent run and the waste figures; they never pretend to have read the code.
- O5: Intake results are cached at `~/.tally/cache/intake/<sha256 of source+title+body+labels+points+model>.json`; a cache hit costs $0 and the task records `cached: true`. `--no-cache` bypasses.
- O6: A receipt records the HEAD it judged. Push, SessionEnd and manual triggers reuse the receipt while HEAD is unchanged; a new commit re-judges; `--force`/`--deep` override.
- O7: The Coach's LLM pass needs session spend ≥ `coach.llm_min_session_usd` ($1); deterministic rules always run.
- O8: `tally_own_usd` is the session's entries in `tally-spend.jsonl` (intake, tiers, coach), no longer the file total plus the judge call again (that double-counted before).
- O9: Fixture replay books each recorded tier call's real cost, so the CI self-share gate (`--max-share 5`) and `baseline.json` reflect live overhead, not stub prices.
- B1: Backfill candidates come from `~/.claude/projects/*/<session>.jsonl` (internal `tally-llm-*` dirs skipped, sessions without prompts skipped), summarised once into `~/.tally/backfill/index.json` keyed by file mtime so `backfill list` is cheap after the first scan.
- B2: Task link order and confidence: URL in a prompt 0.9 → issue key in the branch name or in commits inside the session window 0.6 (`ABC-123`, or `#123` when origin is GitHub) → PR from the session branch 0.7 (needs gh) → none. `--task` overrides with confidence 1.
- B3: Window: start HEAD = `git rev-list -1 --before=<first timestamp> <branch>`, end HEAD = the same at the last timestamp, extended to the merged PR head when gh knows one; a deleted branch falls back to `--all`. No commits inside the window means the session is skipped (uncommitted work cannot be recovered).
- B4: Evidence and checks run inside a detached `git worktree` at the end HEAD; the receipt records the real repo path (`repoCwd`) and `historical.{start_head,end_head,notes}`. The worktree is removed and pruned afterwards, also on failure.
- B5: Historical tests need the same per-repo consent, timeout, process-group kill and scrubbed env. Dependencies are only installed offline (`npm ci --offline --ignore-scripts` with a lockfile; python only with a checked-in venv); otherwise the run is `historical tests not runnable` and test criteria stay unverifiable.
- B6: Intake for backfill uses the ticket as it read at session start when the tracker keeps history (Jira changelog `fromString` replay; GitHub timeline renames plus GraphQL `userContentEdits`), otherwise the current text with a note; the note is stored on the task and shown in the receipt and the grading screen.
- B7: Hook events for past sessions are synthesised from the transcript (prompts, tool calls with results, ship commands, compactions, final message). The Coach replay ticks per event with simulated time, recomputes spend and context from the transcript prefix, applies the normal noise limits, never runs the LLM pass, and writes `coach_replay.json`.
- B8: Blind grading (`calibrate grade`) shows criteria, diff stat, test result, ship/outcome, and the final assistant message, hides Tally's statuses and verdict until the grades are saved, records a `grader` and per-suggestion useful/noise marks, then reveals the comparison. Entries are keyed by session+grader so two people can grade the same session.
- B9: The calibration report adds sample sizes, the lean (Tally more lenient vs stricter than the human), inter-grader agreement when a session has two graders, and Coach precision per rule. Fixture, human and backfill entries are reported in separate sections and never merged.
- B10: `backfill add` prints a projected cost (intake $0.01, tier 1 $0.015, tier 2 $0.12 above the deep threshold, per session) and stops when Tally's actual spend reaches `--max-spend` (default $3).
- G1: Escalation guard. After tier 1, a partial/unmet call on a correctness criterion (behaviour, bug fix, logic, returns/handles/validates, status codes) has its confidence capped at 0.5, and any judgment criterion whose one-step status move would change the verdict is marked `verdict-sensitive`; both escalate to tier 2 regardless of the model's own confidence. Reasons are recorded per criterion in `tiers.escalations` and shown on the receipt.
- G2: Escalation calls re-judge statuses only (`ESCALATION_SYSTEM`, 3k-token pack); tier 1's prose is kept. The tier schema now requires only `criteria`: the strict schema made sonnet exhaust structured-output retries. Internal calls allow up to 4 turns (10 on a max-turns retry) because the structured-output tool needs a second turn.
- G3: Measured floor: every `claude -p` call carries ~5.6k tokens of CLI context, so a sonnet escalation alone is ≈5% of a $0.50 session. Escalations therefore use the small model below `judge.escalation_model_from_usd` ($1), `models.tier2_escalation` (sonnet) up to `deepThreshold`, and `models.judge` (opus, full evidence) above it. On the fixtures this gives 19/19 criteria, 5/5 verdicts, 4.1% average self-share (sonnet everywhere gave 18–19/19 at 5.6–6.7%).
- G4: `calibrate eval --record` writes model outputs and baseline together, and only when criterion agreement is at or above the current baseline; a worse live run leaves both untouched.
- B11: A branch or repo created inside the session has no commit before the start; the window then diffs from git's empty tree so every file counts as added, and the diff base check accepts any tree-ish, not only commits.
- B12: Evidence packs longer than 6k characters go to `claude -p` over stdin with a short `-p` instruction: Windows caps a command line at ~32k characters and a large session's full pack exceeded it (`spawn ENAMETOOLONG`).
- B13: On this machine 43 sessions in 60 days had prompts; 4 had both ≥ $0.50 of spend and commits inside their window and were backfilled ($2.30 of Tally spend, 0.2–2.9% of each session). The other 39 have no commits in their window, so their work cannot be reconstructed from git.

## v0.1 public release (2026-09-16)

- R1: Inferred tasks. With no ticket, intake receives the first prompt plus the branch name and the session's commit subjects, and the task is stored with `inferred: true, confirmed: false`. The Coach rule `task-confirm` shows it once with `[c]onfirm / [e]dit / [l]ink`; `tally task --confirm | --edit | --link` does the same. Receipts, history, reports and calibration carry `task_source: linked | inferred | confirmed`, so accuracy can be split by how the task was defined.
- R2: Transcript-reconstructed diffs. When the session window has no git tree, changes are rebuilt from Edit / MultiEdit / Write calls and shell commands that write files (`sed -i`, `tee`, redirects, `mv`, `cp`, formatters), each labelled `verified-against-disk` when git also saw the file or `reconstructed` otherwise. Tier 1 receives the reconstruction under an explicit "not verified against disk" heading; tests never run without a real tree, so test criteria stay `unverifiable`.
- R3: Inject wording. Every note that reaches Claude starts "Tally observed …" and the hook prefixes it with `Tally:`; the LLM coach is told the same and its output is normalised. `additionalContext` is context, not a command channel, and the wording makes that explicit to the model and to a reader of the transcript.
- R4: Bundle and commit `dist/`. esbuild produces `dist/cli.js` and `dist/hook.js` with zod inlined (no runtime dependencies at all), plus `dist/pricing.json` and the demo fixture. `dist/` is committed because `/plugin marketplace add` clones the repo and runs no build; CI rebuilds and fails on any drift. `tsc` is typecheck-only.
- R5: Plugin hooks use the exec form (`"command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/dist/hook.js", "<event>"]`) so no shell is involved and Windows can spawn it; `tally install` keeps the shell form in `settings.json` for older Claude Code versions, and `isTallyHook` recognises both.
- R6: Double-install guard. `tally install` refuses (exit 1) while `enabledPlugins` has a `tally@…` entry unless `--force`; the hook drops a second delivery of the same (session, event, tool_use_id) via `seen.txt`; `tally doctor` names both installs and which command removes each. Prompts and stops have no id and are not de-duplicated.
- R7: SessionEnd stays inside the shared 1.5 s budget by appending one event and spawning a detached `finalize`; measured 50–80 ms on Windows in the test suite (`TALLY_HOOK_CLI` points the spawn at a stand-in so the test can prove the hook does not wait for the child).
- R8: npm name `@kru3ish/tally` (first available in the requested order; `tally` is taken), binaries `tally` and `cc-tally`, `files` limited to dist, README, LICENSE, CHANGELOG and the plugin files; publishing happens only from the tag-triggered workflow with provenance, never from a laptop.
- R9: Data stays in `~/.tally`, not `${CLAUDE_PLUGIN_DATA}`: receipts must survive plugin updates and uninstalls and be shared with the npm CLI. Documented in the README and SECURITY.md.
- R10: Scrub result. No secrets in the working tree or history (regex pass; gitleaks/trufflehog are not installed here). The only personal identifiers in history are the commit author name/email (git metadata on every commit, not rewritten) and an old README clone URL with the author's username. Fixture paths are synthetic (`C:\Users\dev\acme-app`, `/Users/x/dev/app`).
- R11: Cut from v0.1 (listed in the README): plugin evals (`claude plugin eval`), and the data-dir migration. The demo recording is the real `tally demo` output rendered to an asciinema cast and an animated SVG with synthetic timing, because no screen recorder is installed here; the README says so.
- R12: Calibration numbers for real sessions are `{{CALIBRATION_*}}` placeholders in the README and launch drafts, filled by `scripts/fill-calibration.ts` from `~/.tally/calibration.jsonl` after blind grading. Fixture numbers are written in directly because they are reproduced by CI.
