## Live evaluation through the shipped harness (`tally eval run`, `eval/results/`, `tally eval report`)

Agent: Claude Code (sonnet for the fixture class, opus for real and historical), ≤80 turns, acceptEdits, Tally's hooks attached through `--settings`. Grader: a separate `claude -p` opus process with fresh context that saw the task, the repository and the base commit, never Tally's answer. Every result file keeps the criteria, both sides' statuses and evidence, the agent's commits, per-file counts and (from `e2888fa`) the patch. Nothing was pushed or posted upstream. The ledger's `tally.version` reads 0.6.0 for all of these runs because the version field was bumped only at release; the `commit` field tells the builds apart.

## Defects found by the evaluation and the release audit (all fixed before the 0.6.1 tag, each with a regression test)

1. **`tally verify <session>` from another directory re-judged in that directory and overwrote a correct receipt** with "tests not run: no consent"; the Evidence Map also scanned that directory's test files for keywords. Found on an evaluation session's receipt ten minutes after its worktree was deleted. Verify now follows the repository recorded on the receipt, never re-judges when it is gone, and a tree is scanned only if it contains the receipt's base commit (`7c5f310`). **This is why 0.6.0 is not published.**
2. A test file the agent touched plus a green run anchored any met criterion at VERIFIED (the fixture false VERIFIED). Anchoring needs a test that names the behaviour (`e2888fa`).
3. Generic tokens (JSON, CLI, API, HTTP verbs) counted as keywords a test could name a behaviour with (`7c5f310`).
4. A `file_contains` check whose path is a directory crashed the whole judge with EISDIR, leaving no receipt (two historical sessions). Directories are searched; any check that throws becomes an unverifiable criterion with the error on it (`016d027`).
5. `tally eval run` judged every session twice (the SessionEnd hook's judge and the runner's); on yargs #2423 the two receipts disagreed on the verdict because the maintainer review is a model read. The runner waits for the hook's receipt (`6befb95`).
6. A failed test command counted as failed tests: yargs #2497's `npm test` was red at the base commit from `posttest` lint in untouched files, and Tally marked the behavioural criterion UNMET (the false UNMET). Tally now parses the runner's summary and re-runs the command at the base commit in a throwaway worktree; a green summary with a later-stage failure is UNVERIFIED, a base that fails with the same count stays UNMET with both runs on the evidence line.
7. Unit tests wrote five runs into the real evaluation ledger (`resume-task`); removed, and the runner takes a results root the tests point at a temp dir.
8. The test suite left about 150 directories per run under the OS temp folder; every temp dir a test file creates is now removed when the file finishes.

## Compatibility

36 receipts stored on the release machine (0.1 through 0.6 formats) load and render with the 0.6.x build (release checklist COMPAT). Old receipts without an Evidence Map get statuses derived by rule (`statusFromJudge`); receipts without the new `verification.summary` / `at_base` fields read as before.

## Security

No secrets in fixtures, eval specs or results (release checklist SECURITY, pattern scan). Eval results contain statuses, evidence summaries, costs, commits, per-file counts and the agent's patch; no prompts, no transcripts. The base-commit rerun executes the repository's own test command in a detached worktree with the same scrubbed environment as the independent run.

## Known limitations carried into the release

- Verdict, quality and ROI are experimental, labelled so, and rest on a model score and an estimated human value. The maintainer-review tier's merge / request-changes answer is a model read and was seen to flip between two reads of the same diff.
- A test that names a behaviour but does not exercise it still anchors VERIFIED (mutation verification is roadmap v1.0).
- "Existing behaviour unchanged" criteria are judged, not verified; SUPPORTED is their ceiling and the model's reading can still be generous.
- A suite that is red at the base commit with the same failing count after the work stays UNMET even when the failures are unrelated to the task; the evidence line shows both runs so a reader can dispute it.
- The blind grader is the same model family as the builder; process isolation reduces correlated blind spots, it does not remove them. The human-graded set (11 sessions, 51% exact) remains the reference.
- Trusted publishing to npm is not configured; releases are published manually.
